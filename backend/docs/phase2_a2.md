## عقد Tenant Context

تتحقق Dependency من التوقيع باستخدام Algorithm المحددة في Settings فقط،
ومن `exp` ومن Claims المطلوبة وأنواعها. `sub` سلسلة ID موجبة ضمن مجال
Integer الخاص بالـSchema، و`tid` عدد صحيح موجب، و`ver` العدد الصحيح `2`.
تُرفض القيم النصية أوBoolean بدل الأعداد، والقيم الزمنية غير المحدودة.

تقرأ الحساب من Database باستخدام `(users.id, users.organization_id)`، وتحمّل
المؤسسة والدور والقسم من Database مع إعادة تحميل الحالة الموجودة في Session.
تتحقق من وجود المؤسسة ونشاط الحساب ووجود Password Hash وملكية الدور والقسم.
الدور العام القديم ذو `organization_id=NULL` لا يمنح Tenant Access.

لا تدخل قيم Body أوQuery أوHeader في اشتقاق Context. Routes القائمة تستمر
في استخدام `User` الموثّق لتحديد المؤسسة وفحص مراجع الموارد. Claims مثل
`role`, `permissions`, `organization_id` لا تمنح صلاحية.

تبقى Role Gates الحالية بأسمائها ومعناها. `permissions` مجموعة فارغة ثابتة
لأن A1 لا تعتمد Granular Permission Matrix؛ لا تُخترع صلاحيات جديدة ضمن A2.
المصفوفة التفصيلية والتغييرات الأوسع على Foundation تبقى A4.

## Login وJWT v2

`POST /auth/login` يقبل `application/x-www-form-urlencoded`:

```text
tenant_slug=org-1&email=person%40example.test&password=<password>
```

يُطابق `tenant_slug` قيمة `organizations.slug` كما هي، ثم يبحث عن البريد
داخل هذه المؤسسة فقط. تطبيع طرفي مقارنة البريد هو `lower(btrim(value))`
داخل PostgreSQL، دون Python casefold أوUnicode normalization. تُزال ASCII
Spaces فقط؛ Tabs وNonbreaking Spaces ليست مسافات قابلة للإزالة ضمن هذا العقد.
لا يتغير البريد المخزن أوPassword Hash عند نجاح Login أوفشله.

يرفض Login البريد الغائب أوالفارغ أوالمكوّن من ASCII Spaces فقط صراحةً قبل
اختيار الحساب. فحص الفراغ يستخدم `strip(" ")` فقط؛ تبقى مقارنة البريد
الفعلية داخل Database بالتعبير المعتمد في A1. لا يطابق الإدخال الفارغ حسابًا
ذا بريد فارغ حتى لو دخل هذا السجل بعد Preflight، ولا يعيد كتابة هذا السجل.

الرد الناجح ما زال `{access_token, token_type: "bearer"}`. يصدر Token بالحقول:

```json
{"sub": "123", "tid": 7, "ver": 2, "exp": 1800000000}
```

المثال توضيحي وليس Token فعلية. تبقى مدة Token من Settings، افتراضيًا
120 دقيقة. لا توجد Role أوEmail Claims في Tokens الصادرة الجديدة.
تعطيل الحساب أوتغيير دوره يؤثر في الطلب المحمي التالي حتى لو لم تنته Token.

المؤسسة المفقودة أوالبريد المفقود أوPassword الخاطئة أوعدم جاهزية الحساب
تعيد جميعها `401` مع:

```json
{"detail": "Invalid authentication credentials."}
```

وكذلك `WWW-Authenticate: Bearer`. الحقول الغائبة أوالفارغة تمر بمسار الفشل
نفسه بدل `422` التي قد تعيد Credential Input في تفاصيل Validation.
الـBearer المفقودة أوJWT المرفوضة تستخدم الخطأ نفسه. الحساب الصحيح الذي
يفتقر إلى الدور المسموح للعملية يستمر في تلقي `403` الحالية.

### سياسة bcrypt بعد التصحيح الأمني النهائي

التكلفة الافتراضية الحالية للـHashes الجديدة **12**. يحافظ Login على الـHashes
التاريخية الصحيحة ذات بادئات `$2a$`, `$2b$`, `$2y$` وتكاليف **4–31**، ولا يعيد
كتابة Hash أويرفعها أويخفضها تلقائيًا. التكاليف العالية جدًا مكلفة بطبيعتها؛
الدعم لا يعني أنها مناسبة لتشغيل عام دون ضوابط ومراجعة تشغيلية.

الحد المستهدف لعمل Login هو عمل bcrypt أُسّي يقارب تكلفة **12**:

- الحساب الغائب، والمعرّفات المرفوضة، وHash الغائبة أوالتالفة: فحص Dummy
  بتكلفة 12. تتحقق صيغة Salt قبل استخدامها لأن Salt غير الصالحة قد تُرفض
  فورًا دون تنفيذ العمل المكلف. الـDummy مولدة في الذاكرة وليست Credential.
- Hash صحيحة بتكلفة `c < 12`: تحقق باستخدام Hash الأصلية، ثم فحوص Dummy
  بتكاليف `c, c+1, ..., 11`. إجمالي العمل الأُسّي الاسمي:
  `2^c + (2^c + 2^(c+1) + ... + 2^11) = 2^12`.
  مثال: تكلفة 11 تحتاج فحصًا إضافيًا بتكلفة 11؛ تكلفة 4 تحتاج فحوصًا إضافية
  من 4 إلى 11. عدد الفحوص مختلف لكن ميزانية العمل الأُسّي تتقارب.
- Hash بتكلفة 12: تحقق واحد باستخدام Hash الأصلية.
- Hash بتكلفة أعلى من 12: تحقق باستخدام التكلفة المخزنة دون خفضها أوزيادتها.
  يظل فرق التوقيت مع حساب غائب ممكنًا لهذه الفئة، ولا ندّعي معالجته بالكامل.

تُنفذ هذه السياسة للنجاح والفشل وللحساب غير الفعال. Password فارغة أوتتجاوز
حد bcrypt البالغ 72 byte تُرفض بعد تحقق بديل يخضع للسياسة نفسها، دون قصها.
لا توجد Sleep ثابتة أومعايرة زمنية تعتمد على سرعة جهاز معين.

هذا **تخفيف لفروق التوقيت، وليس Constant-Time Authentication**. توجد فروق
من تهيئة كل فحص وعدد الاستدعاءات واستعلام Database وحمل الجهاز، إضافة إلى
تكاليف Legacy الأعلى من 12. الاختبارات تثبت العمل المنفذ عند حدود bcrypt
والسلوك الوظيفي، ولا تثبت استحالة التعداد بالتوقيت إحصائيًا أوعبر الشبكة.
قبل النشر يلزم جرد تشغيلي مصرح لفئات التكلفة دون كشف Hashes، وتحديد ميزانية
الأداء وRate Limiting مناسبة. لا يجري هذا الطلب جردًا لقاعدة فعلية أويغيّر
سياسة كلمات المرور والحسابات القديمة. لا يسجل الكود Password أوJWT في Logs.

## العضوية والتوافق غير المتوافق

- `legacy`: لا تُطلب طوابع تأكيد مختلقة؛ يلزم النشاط وPassword Hash وصحة
  المؤسسة والدور والقسم للدخول. هويات الدليل دون Password لا تدخل.
- `invitation` و`bootstrap`: يلزم `membership_confirmed_at` و`email_verified_at`
  وPassword Hash غير فارغة، إضافة إلى بقية الفحوص. لا يملأ A2 هذه الحقول.
- لا تنفذ A2 تدفق تفعيل أودعوات أوBootstrap، ولا تنقل حسابًا بين المؤسسات.

التغييرات غير المتوافقة:

1. Login القديمة ذات `username + password` لم تعد مقبولة. يلزم إرسال
   `tenant_slug + email + password` كحقول Form. لا يكفي إضافة Header للمؤسسة.
2. JWT v1 مرفوضة؛ يلزم Login جديد. Passwords وHashes الحالية محفوظة.
3. الحساب غير الفعال يعيد `401` العامة بدل `403` التي تكشف حالة الحساب.
4. `POST /auth/register` يعيد `403` دائمًا ولا ينشئ حسابًا. المسار القديم
   كان يختار أول مؤسسة ودورًا عامًا، ولا يصلح لعقد A1/A2. بديله ضمن A3/A5.
5. خيارات الأدوار تعرض نسخ المؤسسة الحالية فقط؛ مصادر Legacy ليست خيارات.

Frontend الحالية تحتاج تحديث A5 لتبعث Workspace وEmail وتزيل التسجيل القديم.
نافذة OAuth2 الافتراضية في Swagger لا توفر حقل Workspace؛ يمكن تجربة Login
من نموذج العملية ثم استخدام Bearer Token في العميل. A2 لا تنفذ OAuth Server
عامة ولاتغيّر واجهة المستخدم لحل ذلك.

## الاختبارات الآمنة

تثبت الاختبارات: Login صحيحة ومرفوضة، البريد نفسه بمؤسستين، سياسة البريد،
حفظ Hash والبريد، الحساب غير الفعال، العضويات الكاملة والناقصة، الأدوار العامة
والأجنبية، رفض v1 وClaims ناقصة أوغير صالحة وTokens منتهية أوذات توقيع/Algorithm
مختلفة، تجاهل صلاحيات Claims، تغييرات Database اللاحقة، حماية الإدارة والموارد،
وإغلاق التسجيل القديم. اختبارات فساد الحساب تزيل قيودًا محددة فقط داخل Schema
اختبارية مملوكة لإثبات أن التطبيق نفسه يرفض الحالة.

اختبارات التصحيح الجديدة تراقب استدعاءات `bcrypt.checkpw` الحقيقية دون
استبدال نتيجة التحقق. تؤكد ميزانية `2^12` للحساب الغائب والتكاليف 4 و11 و12،
واستمرار تكلفة `2^13` للحساب الأعلى تكلفة. تؤكد كذلك عدم تعديل أي حقل User
في نجاح Login أوفشلها، وتختبر حساب Legacy ذا Hash صحيحة عبر Migrations A1
ثم Login وطلب محمي. لا تستخدم حدودًا زمنية هشة لاعتبار الاختبار ناجحًا.

تحويل Unicode مستقل عن إعدادات Windows. ينشئ Cluster جديدة تحت مجلد مؤقت عشوائي، وPassword عشوائية،
وPort Loopback عشوائية، ثم قاعدة اختبار جديدة وSchema لكل اختبار. لا يقبل
URL خارجية ولايتصل بقاعدة محلية موجودة. يحذف ملف Password بعد `initdb`،
ويوقف Cluster المملوكة وينظف مجلدها بعد الاختبارات. لا توجد Credentials في
argv. عمليات Migration في Regression تخص هذه القاعدة المؤقتة فقط.

## القيود وحالة المراجعة

لا يوجد Session Revocation مستقل أوRefresh Tokens أوRate Limiting جديد في A2.
تغيير Password وحده لا يبطل Token سابقة؛ تعطيل الحساب وتغيير دوره يعاد فحصهما.
لا يثبت نجاح هذه الاختبارات اكتمال عزل جميع وظائف المنصة؛ تبقى أعمال A4
وBatch B/C ضمن نطاقها المعتمد. لا تُعتبر A2 قابلة للنشر منفردة.

يبقى سباق **Last Administrator** في قائمة الإصلاحات المطلوبة قبل النشر:
العد والتعديل الحاليان غير ذريين، وقد يقرأ طلبان متزامنان عدد مسؤولين يساوي
اثنين قبل تعطيل بعضهما. المشكلة سابقة على A2 ولم تُعالج ضمن هذا الطلب،
وفق القيد الصريح. اختبارات منع المسؤول من تعديل نفسه لا تثبت منع هذا السباق.

لا Commit أوPush أوPull Request أوDeployment، ولا تعديل `master` أوRender
أوNetlify أوبيانات قاعدة فعلية. تتوقف المهمة عند A2 للمراجعة.
